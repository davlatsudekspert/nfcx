# PHASE 3 — Android App Architecture

## 3.1 Stack decision

**React Native (bare/community CLI workflow via Expo Prebuild) + TypeScript.**

Rationale, weighed against the brief's own constraints:

- Expo's **managed** workflow is rejected: NFC (`react-native-nfc-manager`), a real
  persistent cookie jar (`@react-native-cookies/cookies`), native contact save
  (`react-native-contacts`), and release-signing control all need native module
  linking Expo Go can't provide.
- Expo is still used as **tooling**, not a runtime cage: `expo prebuild` generates the
  native `android/` project once, after which it's a normal Gradle project. This gets
  us Expo's config-plugin ergonomics (adaptive icon, splash, permissions manifest
  merging) without giving up native module freedom. This is the "Expo Dev Client /
  prebuild" option the brief explicitly allows.
- Plain WebView/Capacitor is rejected per the brief's hard requirement — confirmed
  unnecessary anyway: every screen in the mockup is a genuinely native list/card/sheet
  UI, not a repaginated web page.

## 3.2 Project layout

```
android-app/                      # new top-level folder, sibling to src/server/hosting
  app/                            # screens, one folder per nav destination
  src/
    api/                          # generated-from-Phase-2 typed client (one file per domain: auth.ts, records.ts, auctions.ts, companies.ts, orders.ts, social.ts, content.ts, uploads.ts)
    state/                        # Zustand stores + TanStack Query hooks (see 3.4)
    design-system/                # PremiumButton, PremiumCard, ... (Phase 5 spec)
    navigation/                   # React Navigation stacks/tabs, deep-link config
    native/                       # thin wrappers: nfc.ts, contacts.ts, secureStore.ts, share.ts, haptics.ts
    lib/                          # ported pure logic: pricing.ts, codeTiers.ts, access.ts, music.ts, format.ts
    assets/
  android/                        # generated by `expo prebuild`, then hand-maintained
  __tests__/
```

`src/lib/*` is a **direct TypeScript port** of `src/lib/pricing.js`, `codeTiers.js`,
`access.js`, `music.js`, `format.js` from the web app — same constants, same function
names — so the two clients can never silently drift on tier/pricing display logic.
These files are copied and translated, never imported cross-project (React Native
can't import Vite/JSX-flavored ESM directly, and we do not want a monorepo coupling
that risks accidentally pulling in web-only code).

## 3.3 Networking layer — the one genuinely hard problem in this app

The API is **cookie-session auth only** (Phase 1 §1.4). Design:

1. **`@react-native-cookies/cookies`** as the native cookie store. On Android this is
   backed by `android.webkit.CookieManager`, which persists to disk across app
   restarts and is shared with any in-app WebView (needed anyway for the Yandex Music
   embed and, if ever needed, Payme's hosted checkout page).
2. A thin fetch wrapper (`src/api/client.ts`) that:
   - Always sends `credentials: 'include'` semantics — on Android's `fetch`
     (Networking module → OkHttp) this alone is **not guaranteed** to persist across
     app restarts the way a browser does, hence step 1 backing it explicitly.
   - Reads the current `nfc_session` cookie via `CookieManager.get()` before *every*
     request and mirrors a copy of "logged in: yes/no" (not the raw token) into
     `expo-secure-store` purely so the app can show the right initial screen
     (Login vs Home) before the first network round-trip completes.
   - Centralizes the error-code → UX mapping from API map §2.10.
   - Implements double-submit protection: every mutating call (`POST/PUT/PATCH/
     DELETE`) is deduped by an in-flight-request-key map so a double-tap can't fire
     two purchase/bid/follow requests.
3. **Must be prototyped and device-tested in Phase 5 before anything else** — if
   cookie persistence turns out to be unreliable in practice on some Android/OkHttp
   version combination, the fallback is a small native module that reads/writes the
   `Set-Cookie`/`Cookie` headers directly via OkHttp's `CookieJar` interface. This is
   flagged as the top technical risk of the whole project.
4. `GET /api/settings/payments-enabled` is fetched once at startup and revalidated on
   app foreground; the result lives in a small global store all payment CTAs read
   from (never hard-coded `true`/`false` in a component).

## 3.4 State & data layer

- **TanStack Query (React Query)** for all server data — gives us cache, retry,
  background refetch, and (critically for Auction) **polling** out of the box
  (`refetchInterval`), plus request de-duplication that helps with the double-submit
  concern above.
- **Zustand** for small pieces of client-only UI state (active bottom-sheet, draft
  profile-edit form before save, onboarding step) — deliberately not Redux; nothing
  here needs that much ceremony.
- Auction detail screen: `refetchInterval` starts at 4s while `status==='active'` and
  backs off to 15s when the tab is backgrounded (`AppState`), stopped entirely once
  `status !== 'active'`. Countdown UI itself is computed from `endsAt` with a local
  1s `setInterval` **display** tick — the authoritative time is still the server's, we
  just don't hit the network every second.

## 3.5 Navigation

**React Navigation** (native-stack + bottom-tabs). Structure:

```
RootStack (native-stack, header hidden — PremiumHeader owns chrome)
 ├─ AuthStack            (Splash → Login → Register*)
 └─ MainTabs (bottom-tabs, 5 tabs — brief §14 hard cap)
     ├─ HomeStack         (Home → NfcProfileView → PostDetail…)
     ├─ IdStack           (IdSearch → IdPurchaseFlow(3 steps) → PaymentResult)
     ├─ AuctionStack      (AuctionList(tabs: Live/Upcoming/Ended/Mine) → AuctionDetail)
     ├─ CompanyStack       (CompanyHome → CompanyCreateWizard(5 steps) → CompanyDashboard → CatalogItemEditor)
     └─ ProfileStack       (MyProfile → ProfileEdit → Settings → Notifications**)

* Register screen ships but its CTA is disabled/hidden behind a remote flag until
  Phase 1 §1.6 item 1 is resolved with the backend owner.
** Notifications and Settings are reachable both from the Profile tab and from the
   PremiumHeader's icon buttons (brief's Home screen spec) — same screen, two entry
   points, not a 6th tab.
```

Deep link / App Links (Android) config, mirroring the web routes found in `App.jsx`:

| Web route | Android deep link | Screen |
|-----------|-------------------|--------|
| `nfcstore.uz/:code` (`AAA000` / 8-digit / 3–16 letters) | `https://nfcstore.uz/:code` + `nfcstore://profile/:code` | NfcProfileView |
| `nfcstore.uz/company/:id` | `.../company/:id` | CompanyPublic |
| `nfcstore.uz/c/:id` | `.../c/:id` | CompanyQuickProfile |
| `nfcstore.uz/auksion/:id` | `.../auksion/:id` | AuctionDetail |
| `nfcstore.uz/:code/menyu|mahsulotlar|xizmatlar` | same | NfcProfileView with initial tab |

Android App Links require a `assetlinks.json` on nfcstore.uz signed with the release
keystore's SHA-256 — **needs the real release keystore before this can be verified
end-to-end**, tracked as a Phase 13 dependency, not blocking earlier phases (fall back
to the custom `nfcstore://` scheme during development).

Back-gesture/back-button behavior: predictive-back (Android 13+) handled for free by
React Navigation's native-stack; each bottom-sheet/modal must set its own
`onRequestClose`/gesture so system back closes the sheet before popping a screen
(explicit brief requirement, §19 "back gesture" test item).

## 3.7 Android Contacts permission flow (brief §11)

1. Rationale bottom sheet appears the **first time** the user taps "Kontaktni
   saqlash" (never on app launch) — explains why, in Uzbek, with the exact contact
   fields that will be saved.
2. Only then request `android.permission.WRITE_CONTACTS`.
3. Denied → PremiumEmptyState-style inline message with a "Sozlamalarni ochish" button
   (deep-links to the app's OS settings page) — never a silent failure, never a
   repeated auto-prompt (Android would block it anyway after one denial without
   "don't ask again" being unchecked).
4. Granted → build a contact record: name, phone, email, website (`note` field carries
   the profile URL, since Android's `Contact` model doesn't have a generic
   "profile/company" field the same way iOS's `vCard` ORG line does) — matches brief
   §11's field list.

## 3.8 Security (brief §17)

- HTTPS only — no cleartext traffic (`android:usesCleartextTraffic="false"`,
  Network Security Config pinned to the production host only).
- Certificate pinning: **audited, not force-enabled by default.** Pin Cloudflare's
  leaf/intermediate cert fingerprint behind a remote kill-switch config value, because
  Cloudflare can rotate certs without this repo's involvement — a hard pin with no
  killswitch is exactly the "breaks production cert rotation" failure mode the brief
  warns against (§17). Ship with pinning **off** until the ops owner confirms a
  rotation policy, then flip the flag.
- No secrets in the APK: Payme merchant IDs/keys, admin credentials, D1/R2 credentials
  never appear in client code — the app only ever calls the public REST surface.
- `console.log`/Flipper network inspector compiled out of release builds
  (`babel-plugin-transform-remove-console` + RN's own release-mode Flipper no-op).
- ProGuard/R8 enabled for release; APK inspected for accidentally bundled `.env`/debug
  assets before each release build.

## 3.9 Performance (brief §18)

- Hermes engine (RN default) + RAM bundle / Hermes bytecode precompile.
- `FlashList` (Shopify) instead of `FlatList` for the ID catalog, auction list, and
  company catalog grids — brief explicitly calls out list virtualization.
- Images: `react-native-fast-image` (or Expo Image) for disk+memory caching of
  `/uploads/*` avatars/covers, sized `resizeMode="cover"` requests where the CDN path
  allows.
- Skeleton loaders (PremiumLoadingSkeleton, Phase 5) for every data-dependent screen's
  first paint — no spinners-only states.
- `React.memo`/`useMemo` audit pass at the end of each screen's phase, not deferred to
  the very end of the project.

## 3.10 Testing strategy (mirrors brief §21, mapped to RN tooling)

- **Unit**: Jest for `src/lib/*` ports (pricing/tier classification is pure and
  extremely testable — port the interesting cases from the web app's behavior
  directly as fixtures) and for the API client's error-mapping table.
- **Component**: React Native Testing Library for design-system components (press,
  disabled, loading states) and for screen-level logic (e.g. purchase double-click
  guard).
- **E2E**: Detox on Android emulator for: login → home, ID search → purchase flow
  through to the "pending" state (payments are off, so "success" per se can't be
  E2E-tested against production today — test up to the real 503/pending boundary and
  mock the rest), auction list → detail → bid button honestly disabled, company create
  wizard, contact save permission flow (grant + deny paths), deep link opening a
  profile, rotation or interruption during purchase flow (state survives backgrounding).
- **Manual device matrix**: Android 10/13/14/15 physical or emulator coverage before
  each phase's report, per brief §19.

## 3.11 Package identity

`applicationId "uz.nfcstore.app"` (brief §20). Signing: debug keystore checked in for
CI convenience (already Android tooling default, not a secret); **release keystore is
never generated without the user's explicit go-ahead** (brief §20) — Phase 13 ships a
signing *template* (`keystore.properties.example`, Gradle signing config wired) and
stops there until asked to actually generate and hold a real key.
